# 승인된 제한적 이전 경로 — 2026-10-14

사용자는 전체 j0jn 백업을 추가로 요청하지 않고, 확보한 범위만으로 제한적 이전을
준비하기로 선택했다. 이 경로는 원본 두 DB 전체 이전과 별개이며 손실 없는 전체
복원이라고 표시하지 않는다.

## 준비된 데이터

- 메인 백업의 계정 25개, 심박 22개, 보호자 연결 3개, 처방전 52개 등 기존 기록은
  메인 스키마에 그대로 보존한다. 검토된 legacy 테이블도 별도 archive에 보존한다.
- 약 스키마에는 API에서 확인하고 메인 공통 필드와 대조한 처방전 15개·항목 32개를 넣는다.
- API 목록에 확인된 등록 약 8개만 복원한다. 현재 5개·과거 3개를 구분한다.
  메인의 다른 122개 등록 약을 약 서버에 임의 활성화하지 않는다.
- 공식 의약품 기준 60개와 DUR 기준 1,557개는 메인 백업 출처의 참조 자료로 보존한다.
- API에 없는 복약 일정·완료 로그·실제 복용 시각은 생성하지 않는다.
  날짜별 복용 요약은 비공개 원본 JSON에 남기며 로그로 바꾸지 않는다.
- 복용 시작일·종료일은 API로 검증하지 못했으므로 복원본에서는 미확인(NULL)이다.
  기존 메인의 날짜는 메인 스키마와 원본 백업에 남는다.

**앱 영향:** 현재 약 목록과 처방전 확인은 복원 대상이다. 약 서버의 과거 달력,
복용 완료 이력, 기존 예정 알림과 날짜별 복용 일정은 완전 복원되지 않는다.
새 처방전 등록 및 실제 완료 동작에서 새 일정·로그가 정상 생성되는지는 전환 전
격리 테스트로 검증해야 한다. 기존 약 5개에 대해 복용 날짜/알림을 임의로 재설정하지 않는다.
약 상세의 파생 캐시·DUR 상담 결과는 원본 API 자료로 보존하고 필요 시 공식 자료로
재조회한다. 이 자료를 확인되지 않은 위험 없음 판단으로 바꾸지 않는다.

## 로컬 산출물

비공개 백업 위치의 `medication-partial-verified.db`와 같은 이름의
`.db.manifest.json`이 검증된 후보이다. 초기 `medication-partial-candidate.db`는
개발 중간 산출물이므로 사용하지 않는다. 원본 파일과 후보를 공개 저장소에 넣지 않는다.

생성 도구는 `scripts/prepare_limited_medication.py`이며 원본은 읽기 전용이다.
기존 출력 파일을 덮어쓰지 않는다. 실패한 출력은 import하지 않는다.
계정/약 코드/소유자, 후보 SHA-256, 건수 및 FK 무결성을 확인한다.

이전 준비 도구는 `scripts/migrate_neon_limited.py`이다. 기본은 네트워크 없는 dry-run이다.
같은 Neon DB 안의 `alkong_main`, `alkong_medication` 스키마를 유지한다.
전체 백업용 `migrate_neon.py`의 안전 조건은 완화하지 않았다.

## 실제 적용 전

1. 격리된 PostgreSQL 환경에서 COPY와 새 등록/완료/취소·권한 계약을 검사한다.
2. 인증 설정과 메인/약 서비스 운영 주체를 확인한다. 사용자가 양쪽을 담당할 수
   있도록 Render 접근 또는 단일 담당 배포 경로를 먼저 확보한다.
3. 실제 전환 시 쓰기를 중단하고 메인 최신 백업을 확보한다. 이전 10월 14일
   백업만으로 최신 운영 변경까지 보존된다고 주장하지 않는다.
4. 최신 백업으로 후보와 인증서를 다시 만들고, 비어 있는 Neon 대상에 한 트랜잭션으로 넣는다.
   `--apply --confirm-partial-recovery --confirm-writes-suspended`를 명시해야 적용된다.
5. 양쪽 서버와 새 앱을 함께 전환해 로그인·약 목록·처방전·보호자/심박 연결을 확인한다.

본 준비 작업에서는 Neon에 쓰거나 운영 서버를 재배포하지 않았다.
동료에게 추가 자료를 요청할 필요는 없다. 약 서버에 접근할 수 없는 문제는
기존 서버를 무작정 재배포해서 해결하지 않는다.

## 후속 실제 검증 결과

`scripts/qa_neon_migration.py`를 Neon PostgreSQL 18.6에 실행했다. 실제 사용자
자료가 아닌 합성 데이터만 임시 `alkong_test_*` 스키마에 넣었다.
COPY/내용 해시·유일 ID 충돌 분리·외래키·오류 후 연결 복구·identity 시퀀스·
30개 합성 legacy 행 보존·비어 있지 않은 대상 차단이 통과했다.
검사 후 이 실행의 임시 스키마를 제거했고 남은 테스트 스키마 수 0을 확인했다.
실제 실행에서 발견한 psycopg COPY 커서 생성 호환 문제도 수정했다.

위의 "Neon에 쓰지 않았다"는 운영 자료 이전에 관한 설명이다. 합성 검사에서만
임시 스키마를 생성했다. `alkong_main`, `alkong_medication`, 두 archive의
운영 테이블 수는 여전히 0이고 실제 운영 자료는 아직 전송하지 않았다.

메인에서 SQLite backup API를 다시 실행하여 `main-pretransition.db`를 확보했다.
무결성 ok, FK 오류 0, 기존 백업과 SHA-256 일치다. 쓰기를 중단한 최종 전환
백업은 아니므로 실제 전환 직전에 다시 확인해야 한다.

현재 실제 메인에는 인증 비밀값/서비스 역할/인증 강제 설정이 없다.
Render UI는 로그인이 필요하며 로컬 Render API 키도 없다. 새 코드를 푸시해
자동 배포를 먼저 유발하지 않는다. APK debug 빌드는 성공했지만, DB 전환 후
설정에 맞는 최종 앱 빌드와 재로그인 검사가 별도로 필요하다.
