# 3. 서버 역할·인증·권한 변경

## 3.1. 사용자 인증 흐름

### 3.1.1. 이전 동작의 문제

- 기존 로그인 응답에는 사용자 정보만 있었고 Flutter는 로컬 로그인 표시와 사용자 ID를 저장했다.
- 업무 API 요청에 사용자 토큰이 없었다.
- URL/본문의 사용자 ID가 본인 것인지 증명하는 공통 장치가 없었다.
- 보호자도 전화번호가 같다는 이유로 연결된 계정을 조회 과정에서 자동 채울 수 있었다.

### 3.1.2. 새 동작

1. Flutter가 메인에 가입 또는 비밀번호 로그인을 요청한다.
2. 메인이 계정을 확인하고 `access_token`, `token_type`, `expires_in`을 사용자 응답에 추가한다.
3. Flutter는 토큰을 플랫폼 보호 저장소에 저장한다.
4. 이후 설정된 두 서버에 `Authorization: Bearer <사용자 토큰>`을 보낸다.
5. 메인은 토큰 서명뿐 아니라 현재 계정 존재와 역할을 확인한다.
6. `j0jn`은 서명을 검증하고 메인 내부 경로에서 현재 계정을 확인한다.
7. 본인 대상이 아니면 수락된 보호자 등 허용된 경우에만 처리한다.

### 3.1.3. 토큰 계약과 한계

- 구현 파일: `app/core/auth.py`.
- 형식: payload와 서명의 두 부분으로 된 프로젝트 전용 HMAC-SHA256 토큰. **표준 3부분 JWT라고 가정하지 않는다.**
- 사용자 토큰 수명: 7일. 내부 서비스 토큰 수명: 60초.
- 확인 항목: 서명, audience, subject, role, kind, 발급/만료 시각, 수명 상한.
- 계정 삭제/역할 변경은 다음 온라인 요청에서 거부한다.
- 자동 refresh-token 발급/갱신, 전 기기 강제 로그아웃용 세션 목록은 추가하지 않았다. 토큰 만료 후에는 재로그인한다.
- 오프라인의 계정 삭제/권한 변경을 즉시 감지할 수는 없다. 원본 요구처럼 유효한 기존 세션의 본인 캐시만 허용하며 만료/로그아웃 때 폐기한다.

## 3.2. 내부 서버 요청

### 3.2.1. 용도와 대상 제한

| scope | 주요 용도 | 허용 대상/경로 |
|---|---|---|
| `identity_read` | `j0jn` → 메인 계정 확인 | 메인의 `/api/v1/auth/identity/{target}` |
| `guardian_link_check` | `j0jn` → 메인 보호자 동의 확인 | 내부 authorization 경로, 보호자/환자 ID 일치 |
| `medicine_read` | 메인 AI 상담 → `j0jn` 약 조회 | 대상 사용자의 약 목록 GET |
| `dur_consultation` | 메인 AI 상담 → `j0jn` DUR | 대상 user_id, 목적 consultation인 POST |
| `patient_read` | 메인 보호자 현황 → `j0jn` 환자 자료 | 지정 대상의 허용 조회 경로 |

내부 토큰이라고 모든 사용자·모든 API에 접근하지 못한다. 다른 대상 ID나 다른 용도/쓰기 경로로 재사용하면 거부한다.

### 3.2.2. 약 데이터 계정 동기화

- 이전: 약 조회의 사용자 UUID만으로 약 데이터 DB에 계정 행을 만들 수 있었음.
- 이후: 메인에서 검증한 계정의 최소 정보만 약 데이터 DB에 동기화.
- 동기화: 이름·역할·생년월일·성별·임신 관련 최소 필드.
- 동기화하지 않음: 비밀번호 해시·전화번호 등 계정 로그인 정보.
- 실제 동기화는 운영에서 아직 실행하지 않았다.

연결 수락 PATCH는 환자만, 연결 DELETE는 당사자가 할 수 있다. 온라인 연결 해제 이후 다음 요청부터 환자 접근을 막는다.

### 3.3.2. 대표 실패 응답

- 401: 토큰 없음/유효하지 않음/만료, 현재 계정 확인 실패 중 삭제 등.
- 403: 로그인은 했지만 대상/용도에 대한 접근 권한이 없음.
- 404: 없는 연결/리소스 또는 허용하지 않은 관리 경로 등.
- 409: 심박 요청 ID 내용 충돌, 복약 상태 불일치 등.
- 503: 상대 인증 서버를 확인할 수 없는 경우 등. 권한 조회 실패를 허용으로 바꾸지 않는다.
- 시작 실패: 필수 운영 인증 설정 누락. 이는 정상적인 fail-closed 안전장치다.

## 3.4. 보호자 동의의 세부 조건

### 3.4.1. 새 연결

- 전화번호만 저장된 연락처는 연결 계정이 확인되고 동의가 있는 연결과 다르다.
- 보호자가 기존 전화번호 연락처와 매칭되는 계정으로 요청하면 PENDING으로 묶고 환자의 수락을 기다린다.
- 환자가 로그인한 상태에서 이미 존재하는 보호자 계정을 직접 지정해 등록하는 기존 경로는 환자 본인의 동의로 ACCEPTED와 동의 표식을 남긴다.
- 따라서 **모든 새 연결이 무조건 PENDING이라는 설명은 정확하지 않다.** 전화번호만 등록했다고 미래의 계정이 자동 승인되는 것은 막았다.

### 3.4.2. 기존 데이터의 마이그레이션

- `guardians.consent_verified_at` 추가.
- 기존 `requested_by=GUARDIAN`이고 수락된 계정 연결은 동의 표식을 채워 유지.
- 기존 `requested_by=PATIENT`의 수락 행 중 동의 표식이 없으면 자동 연결의 위험을 배제할 수 없어 재수락 PENDING으로 전환.
- 연락처·연결 ID 자체를 삭제하지 않는다. 상태/동의 메타데이터의 변경은 의도된 변화이며 '모든 열이 완전히 불변'은 아니다.
- 이 과정은 로컬 사본에서만 검증했다. 실제 운영 연결에 적용한 것은 아니다.

# 4. DB 보존·처방전·복약·심박 변경

## 4.1. 마이그레이션 및 보존

### 4.1.1. 구현

- `init_db.py`: `initialize_database(preserve_records=True)` 경로 추가.
- 기존 테이블을 임의로 이름 변경/대체하지 않는 추가 마이그레이션.
- 한 트랜잭션에서 실행하고 실패하면 롤백.
- 기존 구조가 필요한 필수 열과 호환되지 않으면 무리하게 바꾸지 않고 실패.
- 보존 모드에서는 기존 시연 약 비활성화/OCR placeholder 정리 작업을 건너뜀.
- 인증을 켠 OCR/처방전 확정에서도 전역 placeholder 삭제를 하지 않음.

### 4.1.2. 보존 도구

- `scripts/hardening_database.py` 추가.
- 기본 실행은 원본을 읽기 전용으로 열고 SQLite backup API로 임시 사본을 생성.
- WAL 변경분을 포함하는 일관된 백업 후 사본에서 두 번 마이그레이션.
- integrity, foreign key, 기존 보호 대상 행의 열/건수/hash 비교.
- 기존 테이블이 없어서 새로 생긴 빈 테이블은 허용.
- 보호자 상태/동의 열은 의도한 동의 마이그레이션 때문에 불변 비교에서 제외.
- `--apply`는 새 `--backup` 경로가 필수. 기존 백업 덮어쓰기 금지.
- 실행 성공 출력은 건수/검증 결과뿐이며 개인정보 행이나 비밀값을 출력하지 않음.
- **이 도구가 있다고 운영 백업이 이미 생긴 것은 아니다.**

## 4.2. 처방전 등록

### 4.2.1. 실제 바뀐 부분

- `prescriptions.registration_revision INTEGER NOT NULL DEFAULT 1` 추가.
- 정확히 같은 registration fingerprint는 기존 처방전 ID 재사용.
- 확정 처리에 BEGIN IMMEDIATE를 사용해 중복 확정 경쟁을 줄임.
- 재등록 시 과거 복약 로그와 연결된 일정을 삭제하지 않음.
- 다른 처방전으로 같은 약을 다시 등록할 때도 과거 로그가 있는 일정은 유지.
- 정리 가능한 것은 등록일 이후의 PENDING·로그 없는 일정에 제한.
- 결과 응답에 `registration_revision` 포함.

### 4.2.2. 추가하지 않은 정책

- 사용자가 내용 일부를 고치는 기존 처방전 수정 API 및 revision 증가 정책을 새로 정의하지 않음.
- 원본은 열 추가와 동일 처방전 ID 보존을 요구했으며, 안정적인 정정 식별 계약을 제시하지 않았음.
- 내용 변경으로 fingerprint가 달라지면 기존 규칙대로 새 처방전.
- 비슷한 병원·날짜·약 이름만 보고 같은 처방전으로 합치는 구현은 없음.

## 4.3. 복약 완료·취소

### 4.3.1. 현재 상태와 감사 기록

- `medication_schedules.status`: 현재 상태의 기준.
- `medication_logs`: 변경 이력. 기존 TAKEN을 지우지 않음.
- 완료: TAKEN 로그 + 일정 TAKEN.
- 취소: CANCELLED 로그 + 일정 PENDING.
- 재복용: 새 TAKEN 로그 + 일정 TAKEN.
- 같은 현재 상태에 대한 재시도는 중복 이력 없이 기존 결과를 반환하는 경우를 처리.

### 4.3.2. 여러 약을 함께 처리

- Flutter가 시간대의 모든 약에 해당하는 schedule_id를 한 번에 전송.
- 서버는 요청 일정의 소유자/존재를 모두 확인하고 한 트랜잭션으로 처리.
- 하나라도 없거나 다른 사용자 일정이면 전체를 실패 처리.
- Flutter도 일정 ID가 하나라도 빠지거나 중복이면 일부 약만 완료시키지 않음.
- 서버 결과의 일정 ID와 상태까지 확인한 뒤 화면을 변경.
- 취소 UI도 서버 응답을 기다린 뒤 완료 표시/알림 상태를 되돌림.

### 4.3.3. 조회의 변경

- 홈·기록·미복용 판단·보호자 활동 조회가 예전 TAKEN 존재만으로 완료라고 판단하지 않도록 수정.
- 보호자 현황은 메인 DB의 빈 약 목록이 아닌 `j0jn`의 실제 약/복약 정보를 내부 인증 조회.
- 조회 실패 시 0건/정상 상태로 숨기지 않고 실패를 전달.

## 4.4. 심박 저장과 범위 안내

### 4.4.1. 중복 방지

- `heart_rate_logs.client_request_id` 추가. 과거 행은 NULL 그대로.
- 사용자+요청 ID의 NULL 제외 유일 인덱스.
- 같은 ID/같은 내용은 기존 log ID 반환.
- 같은 ID/다른 BPM·기기·출처·측정 문맥·명시 시각이면 409.
- Flutter의 세 심박 저장 경로에 측정 단위의 요청 ID 연결.
- 요청 ID를 붙이지 않은 기존 호환 요청에는 새 ID 기반 중복 방지가 적용되지 않는 점에 유의.

### 4.4.2. UI 표현의 범위

- 60 미만: 참고 범위 아래.
- 60~100: 참고 범위 안.
- 100 초과: 참고 범위 위.
- 측정 이탈을 기록/안내하는 것이며 의료적 정상/이상 확정이나 응급 판단이 아님.
- 기존 기준 심박 및 측정 기록을 삭제하거나 일괄 바꾸지 않음.

# 5. Flutter 변경 및 화면 예시

## 5.1. 예시 해석 방법

### 5.1.1. 실제 운영 화면과 구분

### 5.2.1. 사용자에게 보이는 변화

- 명시적 mock 화면 확인과 실제 백엔드 사용자 ID만으로 로그인하는 우회는 구분. 실제 계정 우회에는 유효한 저장 인증이 필요.

기존 계정을 새로 가입시키거나 비밀번호를 바꾸는 기능을 구현한 것은 아니다.

### 5.3.2. 예시

```text
오프라인 · 저장된 내 정보만 보고 있어요.

내 약
```

## 5.4. 오늘 홈·쉬운 화면·복약 완료 화면

### 5.4.1. 완료와 취소의 변화

- 기존 약 이름/사진/하루 횟수 표시를 다른 양식으로 덮어쓰는 작업은 하지 않음.
- '먹었어요'는 시간대의 여러 약 저장이 모두 확인된 뒤 완료 표시.
- 취소는 서버 저장이 확인된 뒤 해당 시간대의 미완료 상태로 돌아감.
- 일반 홈, 쉬운 복약 흐름, 복약 완료 화면의 취소 호출부를 비동기 처리/오류 안내에 맞춤.
- 취소 실패 시 기존 완료 상태 유지.

### 5.4.2. 예시

```text
아침 약 3종 → 먹었어요
→ 3개 일정 모두 서버 저장 성공
→ 아침 복약 완료

취소 선택
→ 3개 일정 CANCELLED 감사 기록 + 현재 PENDING
→ 오늘 홈에서 아침 복약 미완료
→ 새로고침/다른 기기 조회도 미완료
```

```text
3종 중 1종의 일정 ID가 없음
→ '모든 약의 복약 일정 정보를 확인하지 못했어요.'
→ 2종만 저장하고 전체 완료라고 표시하지 않음
```

## 5.5. 보호자 연결·돌보는 분·알림 안내

### 5.5.1. 연결 화면에서 달라지는 결과

- 기존 전화번호만 기록된 연락처가 추후 가입한 계정으로 자동 공개되지 않음.
- 필요한 연결은 환자의 재수락 PENDING으로 나타날 수 있음.
- 수락 후 연결 환자의 약·복약·심박 조회.
- 해제 후 다음 온라인 조회에서 환자 정보를 거부.
- 실제 기존 운영 연결의 상태 변화는 아직 적용하지 않았음.

### 5.5.2. 돌보는 분 화면

- 화면이 현재 경로이고 '돌보는 분' 탭이며 앱 전경일 때 30초 주기 재조회.
- 다른 경로/정보 탭/백그라운드에서는 주기 조회 요청을 건너뜀.
- 화면 dispose 시 타이머와 관찰자 제거.
- 구현은 보호자 홈 현황 provider 갱신이다. 모든 하위 상세 화면/앱 종료 상태의 실시간 스트리밍을 구현했다는 뜻이 아님.

### 5.5.3. 알림 설정 → 지원 범위 안내

```text
알림 안내

보호자가 확인할 수 있는 것
앱을 열어 돌보는 분의 복약 상태와 심박 기록을 확인할 수 있어요.
돌보는 분 화면을 보는 동안 새 정보를 주기적으로 조회합니다.

현재 지원 범위
환자 휴대폰의 복약 시간 알림과 앱 안의 기록·알림을 지원해요.
보호자에게 문자나 앱 종료 중 푸시를 보내지는 않아요.
밤 시간 소리 설정도 아직 지원하지 않아요.
```

문자/종료 중 보호자 푸시/야간 소리 제어 스위치를 실제 가능한 설정처럼 제공하지 않는다. 환자 휴대폰의 기존 로컬 복약 알림은 없애지 않았다.

## 5.6. 심박 화면

### 5.6.1. 표시와 저장

- 참고 범위 아래/안/위로 안내 문구 정리.
- 측정값 자체를 바꾸지 않음.

## 5.7. OCR·내 약·약 자세히·AI 약사

### 5.7.1. 유지한 화면과 바뀌는 처리

# 7. 의도했지만 끝내지 못한 작업과 그 이유

## 7.1. `j0jn` 필수 인증 환경변수 등록

### 7.1.1. 하려던 것

두 서버에 같은 비밀값을 넣고 역할과 상대 URL을 지정해 실제 인증 강제로 전환하려 했다.

### 7.1.2. 실제 확인과 미완료 이유

- `j0jn` Environment의 전체 이름 목록에서 아래 이름이 없다.
  - `SERVICE_ROLE`
  - `AUTH_ENFORCED`
  - `ALKONGYAKONG_AUTH_SECRET`
  - `AUTH_AUTHORITY_BASE_URL`
  - `ALKONGYAKONG_DB_PATH`
- 연결된 환경변수 그룹도 없다.
- 환경변수의 비밀값은 열거나 복사하지 않았다.
- 메인에는 같은 비밀값이 필요하지만 해당 운영 설정에 접근/확인하지 못했다.
- 브라우저에서 새 인증 비밀값을 입력/저장하는 작업은 사용자/서버 담당자의 직접 입력이 필요한 인계 항목이다.
- 한쪽만 설정/배포하면 전체 앱 흐름이 깨질 수 있어 실제 전환을 하지 않았다.

## 7.2. 영구 저장소와 운영 DB 백업

### 7.2.1. 하려던 것

기존 두 DB를 일관되게 백업하고 영구 디스크 위에서 사본 검증/추가 마이그레이션을 실행하려 했다.

### 7.2.2. 실제 확인과 미완료 이유

- `j0jn`은 현재 Free compute plan.
- Disk 화면에 무료 compute plan에서는 Disk 미지원이라고 표시.
- 무료 플랜의 Shell/SSH 등도 유료 기능 안내에 포함.
- 운영 DB/WAL의 안전한 원본 사본을 아직 확보하지 못했다.
- 영구 디스크를 위한 유료 전환/비용 결정을 임의로 할 수 없다.
- 플랜 변경·재배포가 기존 임시 파일을 잃게 할 수 있으므로 백업 전에 먼저 바꾸지 않았다.
- Git에 있는 로컬 DB를 운영 DB라고 간주하지 않았다.
- 공개 무인증 DB 다운로드/수정 API를 만들어 우회하지 않았다.

**후속:** 담당자가 기존 운영 DB의 안전한 확보 방법과 저장소 비용을 먼저 결정해야 한다. 이 문서는 무료 인스턴스에서 원본을 안전하게 확보하는 방법을 이미 해결했다는 보증이 아니다.

## 7.3. 같은 코드의 두 서버 동시 전환

### 7.3.1. 하려던 것

백업·설정 준비 후 같은 커밋을 두 Render에 배포하고 실제 API를 확인하려 했다.

### 7.3.2. 하지 않은 이유

- 앞의 백업/영구 디스크/인증 설정이 선행되어야 함.
- 새 코드가 `RENDER` 환경에서 필수 설정 누락 시 기동을 거부하도록 구현되어 있음.
- 현재 `woong2`는 `j0jn` 배포 대상. 푸시가 배포를 일으킬 가능성이 있음.
- 메인 Render의 자동 배포 브랜치/환경 설정은 확인하지 못함. main 업로드와 실제 배포 준비 완료를 혼동하면 안 됨.
- 사용자 요청으로 Git main 반영을 별도로 진행하더라도 새 서버 설정과 운영 검증 완료라고 표시하지 않음.
